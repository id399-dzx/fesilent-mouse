> 等次日指示再开工）。任务编号 **T-508**。对应需求 **FR-501**（原生拖放，此前列为 P2 打磨项）。

## 1. 目标与用户故事

**目标**：让"跨机传文件"像在同一台机器上拖文件一样自然。

**用户故事**：
> 我在 A 机用鼠标按住一个文件开始拖动，鼠标拖着它移到屏幕边缘、穿越到 B 机的屏幕，
> 在 B 机某个 Finder/资源管理器窗口（或桌面）上松手——文件就出现在我松手时鼠标
> 所在的那个文件夹里。

与**已有**的"粘贴式"文件传输（T-504：复制→穿越→落到接收目录 + 写回剪贴板供 Cmd+V）的关系：
- 粘贴式是 **FR-502 的兜底交互**，已实现、保留。
- 本特性是 **FR-501 的原生体验**，是更自然的上层交互，**不替换**粘贴式（拖放风险高时仍可退回粘贴式）。

## 2. 验收标准（建议）

1. A 上拖一个文件穿越到 B 的某文件夹窗口松手 → 文件出现在该文件夹，内容 sha256 一致。
2. 拖到 B 桌面松手 → 落到桌面。
3. 拖动过程中 A 上能看到"正在拖动/即将跨屏"的反馈；B 上能看到落点高亮（尽力而为）。
4. 拖到非法落点（无写权限/非文件夹区域）→ 回退到默认接收目录并提示（不丢文件）。
5. 大文件复用 T-506 的 >1GiB 确认与进度/取消。

## 3. 为什么这件事不简单（先认清难点）

跨机拖放不是"鼠标穿越 + 文件传输"的简单叠加，难点在**两端各自的原生拖放会话**：

- **源端 A**：当前 daemon 只看到底层鼠标事件（CGEventTap / 低级钩子），**看不到"用户正在拖一个文件"
  这个语义**。要知道"拖的是哪个文件"，必须接入 OS 的拖放会话（mac `NSDraggingSource` /
  Windows OLE `DoDragDrop`），或在拖动开始时从被拖对象取文件引用。
- **目标端 B**：要把文件"放进鼠标所在的文件夹"，必须知道光标下是哪个窗口/哪个文件夹
  （Finder/Explorer 的视图 + 路径），并最好触发一次**原生 drop**让目标应用自己落地。
  这要用辅助功能/UI 自动化或合成 OLE drop，平台差异大、边界多。
- **跨进程/跨机**：原生拖放是单机 OS 概念，跨机必须"在 A 拦截拖放 → 网络传文件 →
  在 B 重建一次落地"，中间是我们自己的协议。

参考：Synergy/Deskflow 有跨屏拖放，但实现复杂且我们**禁止复制其代码**（GPL），只可看思路。

## 4. 总体方案（建议路线）

分两层：**传输层复用**（已有）+ **两端拖放桥接**（新增、平台相关）。

```
A 机                                            B 机
拖动开始：取被拖文件路径                          鼠标命中边缘(已有 engine 边缘穿越)
   │                                            │ CONTROLLED：注入鼠标移动
   │  鼠标移到边缘 → engine 进入 REMOTE(已有)     │
   │  ── 检测到"拖动中 + 跨屏" ──▶ 标记 drag 会话  │
   │  ── 鼠标移动经 datagram 注入(已有) ────────▶│ 光标在 B 上移动，B 上呈现"拖入"反馈
   │                                            │
松手(mouse up)：                                 │
   │  ── DragOffer{files} 经独立流 ────────────▶│ 读光标位置 → 求目标文件夹
   │  ── FileChunk…（复用 ms-net::transfer）───▶│ 落到目标文件夹（或原生 drop）
   │                                            │ 失败回退默认接收目录
```

### 4.1 复用已有
- **边缘穿越/坐标映射**：ms-core engine（§5.1）已做，拖动时光标穿越走同一套。
- **文件传输**：`ms-net::transfer`（send_file/recv_on_stream + 进度/取消）直接复用；
  新增的只是"落点目录由光标决定"而非固定接收目录。
- **传输中心 UI**：T-506 的 `app/transfers.rs` 进度/取消/大文件确认沿用。
- **协议**：可新增一条消息 `DragOffer{ files, drop_x, drop_y }`（编号见 SPEC §3，
  **新增编号需在 wire.rs 锁定并更新 SPEC**），或复用 FileOffer 再带落点坐标。

### 4.2 新增：源端 A 的"拖动会话"检测
- 需要在**拖动开始**时拿到"被拖的文件路径"。两条可能路线：
  - **路线 A（原生拖放源）**：app 注册为拖放源/监听系统拖放会话，拿到拖动的
    `NSDraggingItem` / OLE `IDataObject` 里的文件。最"正"，但要深入平台拖放 API。
  - **路线 B（近似）**：检测"鼠标在文件上按下并移动"时，从当前 Finder/Explorer
    选中项取文件（辅助功能 API 读选中）。简单些但不够准（拖的不一定是选中项）。
- 判定"拖动中跨屏"：engine 进入 REMOTE 且左键处于按下态（inject 层已跟踪 drag 状态，
  见 `platform-macos/inject.rs` 的 `drag` 字段思路）。

### 4.3 新增：目标端 B 的"落点文件夹"解析
- 松手时取 B 上光标全局坐标 → 命中测试找窗口 → 判定是否 Finder/Explorer 视图 →
  求其当前目录路径。
  - **mac**：Accessibility（AXUIElement）按坐标取元素 → 找所属 Finder 窗口 → 取其
    `AXDocument`/目标 URL；或 Apple Events 问 Finder「front window 的 target」。
  - **Windows**：`WindowFromPoint` → 判断是否 Explorer（`CabinetWClass`/`ShellTabWindowClass`）
    → 经 Shell 接口（IShellBrowser/IShellView 或 UIAutomation）取当前文件夹路径。
- **降级**：解析不到目录 → 落到默认接收目录（`Downloads/MouseShare`）并提示（不丢文件）。
- **进阶（可选）**：在 B 合成一次原生 drop，让目标应用自己处理（更自然，但更难、更脆）。

### 4.4 平台 API 速查（实现时再深入，先登记）
| 能力 | macOS | Windows |
|---|---|---|
| 取被拖文件（源） | NSDragging / NSPasteboard 拖动板 | OLE `DoDragDrop` / `IDataObject`(CF_HDROP) |
| 光标下窗口/文件夹（目标） | AXUIElementCopyElementAtPosition + Finder AX/AppleScript | WindowFromPoint + Shell/UIAutomation |
| 合成 drop（可选进阶） | NSDraggingDestination 模拟 | `IDropTarget::Drop` / SHDoDragDrop |

均为 `unsafe` FFI，按 CLAUDE.md §5 隔离在 platform-* crate，每处 `// SAFETY:`，并把
新踩坑登记进 TECH-REVIEW。

## 5. 建议的子任务拆分（实现阶段再认领）

1. **T-508a 协议**：定 DragOffer 消息（或扩展 FileOffer 带落点），wire.rs 锁编号 + SPEC §3 更新 + round-trip 单测。
2. **T-508b 源端拖动检测（mac 先行）**：拖动开始取文件路径 + 跨屏判定；纯逻辑可单测，平台部分本机实测。
3. **T-508c 目标端落点解析（mac 先行）**：光标坐标→Finder 目录；解析不到则降级默认目录。
4. **T-508d 接线 daemon**：拖动跨屏 → 松手 → DragOffer → transfer → 落目标目录（复用 T-506 进度/取消/大文件确认）。
5. **T-508e Windows 侧**：Explorer 目录解析 + 拖动源；交叉编译 + 真机（H-2）。
6. **T-508f 落点反馈/降级提示 UI**。

每个子任务遵守三连门槛 + 平台真机登记 H-2/H-5（CLAUDE.md §4）。

## 6. 开放问题（需实现前或过程中拍板）
- 源端拿被拖文件用"原生拖放源(路线A)"还是"读选中项(路线B)"？影响准确度与工作量，**建议先问用户/先做路线B验证可行性**。
- 目标端是"我们直接写文件到解析出的目录"还是"合成原生 drop 交给目标应用"？前者稳、后者自然；**建议一期先写文件到目录**。
- 落点解析失败的降级体验（提示形式）。
- 是否需要拖动过程中的跨机视觉反馈（光标旁文件图标 / 落点高亮）？一期可不做。
- 与粘贴式（T-504）的优先级/共存：两者都在"切换/松手时读剪贴板或拖动项"，注意去重与触发条件不要打架。
